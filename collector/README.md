# 収集基盤（宣言＋パーサ）

**新しい収集を追加する手順は2つだけ**:
1. `sources.py` にパーサ関数を1つ書く（`text -> list[dict]`）
2. 同じファイルの `SOURCES` に宣言を30行足す

これだけで、以下が**自動で**付いてきます:

| ガード | 中身 | 由来した事故 |
|---|---|---|
| 礼儀つき取得 | ホスト別のレート制限・指数バックオフ・429はRetry-After尊重・keep-alive・gzip | Open-Meteoの429で提出ジョブ停止（8/21-22） |
| IPv4強制（任意） | `fetch: {ipv4: true}` | NASAへIPv6で到達できずCI失敗（8/23） |
| 生情報の保存 | `raw: {save: true}` で構造化した中身を日付つき保存 | 抽出後の1数値しか残さず、後から問い直せなかった（8/24） |
| 重複排除・追記 | keyで冪等に台帳へ追記 | — |
| **件数とスキーマの検査** | `expect: {rows: [lo,hi], schema: [...]}` を外れたら**失敗させる** | パーサ破損で0件でも「成功」になる沈黙（#18の系統） |
| 障害ログ | `docs/incidents.md` へ自動追記 | 手で埋めて真因が4日隠れた（8/19） |
| 原子的書き込み | tmpへ書いてreplace | 途中で落ちた時に壊れたファイルを残さない |

## 作らないもの（意図的な線引き）

汎用ETL・スケジューラ・ワークフローエンジン・UI・DB。**GitHub Actionsとgitで足りている部分は置き換えない**。この骨格の目的は「同じ穴が二度と開かないこと」であって、基盤を持つこと自体ではない。

## 移行の状況（2026-08-24・全面移行）

**方針（Haruki）**: 「基盤構築だから多少保守が重くなっても、そっちに寄せる安心感を得たい」——
1ソースのためでも抽象を足し、**例外を作らない**方向で統一した。

| 対象 | 方式 | 備考 |
|---|---|---|
| 出力制御・書籍 | **宣言＋パーサ**（sources.py） | ガードが全部付く完全形 |
| JEPXスポットCSV | ランタイム経由（**bytes版**） | cp932の往復デコードで中身が変わる事故を実測→bytes版を追加 |
| 気象（Open-Meteo 8地点） | ランタイム経由 | 429のRetry-After尊重を共通化 |
| 地震（P2P API） | ランタイム経由 | |
| 気象庁JSON・GDACS RSS | ランタイム経由 | |
| FIRMS | ランタイム経由（**ipv4: true**） | IPv4強制をランタイムの機能へ昇格 |
| **青果（ベジ探）** | ランタイム経由（**POST**） | この1本のためにランタイムへPOSTを追加 |
| **衛星のSTAC検索** | ランタイム経由（POST JSON） | |
| 衛星のCOG読み出し | **設定で統一** | rasterio(GDAL)が内部でHTTPレンジ取得するため経路は寄せず、リトライ・待機・タイムアウト・不要なHEAD抑制をGDAL環境変数で同じ思想に揃えた |

**残る例外はゼロ**（COGは経路でなく設定で統一）。

## 実行

```bash
python3 collector/collect.py            # 全ソース
python3 collector/collect.py tohan_books   # 個別
```

# 収集対象を増やすときの運用（2026-08-24）

## 0. まず「増やしてよいか」を判定する

| 関門 | 基準 | 根拠 |
|---|---|---|
| **無停止率** | 直近30日で**全リーグ95%以上**（`docs/uptime.md` が⛔なら追加禁止・修理が先） | 本数を増やすほど故障モードが増える。10日で障害5件を出した実績 |
| **財布への接続** | その素材が**どの事業仮説の判定に効くか**を1行で言えること | 外部レビュー指摘「素材棚の採点軸に財布が無い」。書籍・山火事は接続が弱い |
| **象限の重複** | 既存10本と同じ象限（価格/物理/制度/文化）を増やすなら、**なぜ2本目が要るか**を書く | 同じ市場を3本見ても新情報は増えない |

## 1. 実地で確認する（採点表を信用しない）

**ページを実際に開くまで「入手できる」と判定しない。** 出力制御（S8）で入手性を4点と採点したが、実際に2枚読んだら実績は非公表で2点に訂正した。

- [ ] 目的のデータがHTMLに実在するか（PDFのみ・JS描画のみ、はよくある。書籍のジャンル別はPDFのみだった）
- [ ] **過去分が取れるか**（取れる＝再取得可能＝格付けC寄り。取れない＝一回性＝格付けA）
- [ ] robots.txt と利用規約
- [ ] 更新頻度と、**予測対象にできる「正解ラベル」が毎回必ず出るか**

## 2. 実装する（パーサ1関数＋宣言30行）

```python
def parse_xxx(text: str) -> list:
    ...
    return [{"id": ..., "date": ..., "value": ...}]   # idは重複排除の鍵

SOURCES["xxx"] = {
    "name": "xxx", "url": "...",
    "fetch": {"interval": 2.0, "retries": 4},   # ipv4/data(POST)も指定可
    "raw": {"save": True},        # 一回性があるなら必ずTrue
    "expect": {"rows": [lo, hi], "schema": ["date", "value"]},
    "parser": parse_xxx, "cadence": "...", "grade": "A/B/C", "note": "...",
}
```

礼儀・バックオフ・429対応・生の保存・重複排除・件数/スキーマ検査・障害ログ・原子的書き込みは**ランタイムが引き受ける**。

## 3. 検証する（鳴らないアラートは無意味）

- [ ] `python3 collector/collect.py xxx` が通る
- [ ] **故障注入**: 0件・列欠け・件数異常の3つで `check_expectations` が鳴る
- [ ] `raw/xxx/YYYY-MM-DD.json` に中身が残っている
- [ ] `python3 smoke_test.py` が通る（宣言の必須項目とマニフェスト登録を自動検査）

## 4. 台帳へ登録する

- [ ] `data_manifest.json` に追加（`python3 data_guard.py --update` で状態を記録）
- [ ] `.github/workflows/collector.yml` のスケジュールに載る（既定の2回で足りるか確認）
- [ ] 本社 `docs/experiments.md` の素材棚に状態を書く
- [ ] **公開ダッシュボードに載せる**（`build_site.py` のパネル＋`site_template.html` のナビ＋JSのid配列の3箇所）。
  2026-08-24にリーグを4本作ってここを忘れ、**ダッシュボードだけ6本のまま**になっていた。
  採点前は「収集中（N件）」、採点後は成績表に切り替わるように書く——空パネルが並ぶと
  「動いていない」と「まだ始まっていない」が混ざる

## 5. やめるときの扱い（**自動停止はしない**・2026-08-24 Haruki指示）

- **収集を自動で止めることはしない。** 90日間どの分析にも使われていない収集があれば、**月次レビューで「停止の提案」として挙げるだけ**にする。判断はHaruki
- 理由: 使われていないことと価値がないことは別。**一回性のデータは、止めた瞬間に二度と埋められない空白ができる**（GDACSで既にRSSから落ちた62件を取り逃している）。「いま使っていない」を理由に機械が止めると、後から効く素材を機械の判断で殺すことになる
- 実際に止める場合のみ、宣言に `"retired": "YYYY-MM-DD 理由"` を残す（消さない——なぜやめたかが次の判断材料）
